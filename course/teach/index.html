At a glance

Audience. Security professionals who know prompt injection from chatbots and may not yet think of an agent’s tool list as an attack surface. The module is written for blue and red teams together: red sections borrow the agent’s authority, blue sections size, scope and check it.

Needs. A modern browser. No key, no install, no network after the page loads. The lab is a deterministic stand-in, so every run is the same and safe for a stage.

Outcomes. A learner can (1) audit a tool list against one task and name each surplus tool as excessive functionality, permissions or autonomy; (2) write a task-scoped credential, an object check and an approval gate and show which layer held each of four attacks; (3) say why a rule on a command string is a guess and a typed tool is not; (4) say what a pin, a scanner and a reach limit each catch in a poisoned tool; (5) produce a tool register for their own agent and a test that fails if its policy slips.

The sentence to leave on the wall. Authority is a property of the call, not of the agent: shrink the toolbox, scope the credential to the task and the person, and check every use outside the model.

Honest framing, to say early. Nothing in this module measures a real model. The assistant makes the calls a fooled model would make, in a fixed order, so what the page tests is the deployment around it. For a measurement of real models, send people to the model benchmark tool, which runs Module 02’s attack set on their own key.

Answer key

The four code exercises
def mint(task, user):
    if task not in TASKS or user not in STAFF:
        raise PermissionError("unknown task or person")
    return {"sub": f"task:{task}:{user}",
            "scopes": sorted(TASKS[task]["scopes"]),
            "tenant": STAFF[user]["tenant"]}

def can_access(cred, acct):
    tenant = cred.get("tenant")
    return bool(tenant) and acct.get("tenant") == tenant

def needs_approval(call, sent):
    tool = call["tool"]
    if tool == "send_email":
        return sent >= FLOOD_AFTER
    return TOOLBOX[tool]["irreversible"] or tool == "export_csv"

ALLOWED = {"-i", "-n", "--ignore-case", "--line-number"}
def valid_flags(flags):
    return all(token in ALLOWED for token in flags.split())

The page grades each on the cases shown in its results table, and the engine’s own self-check runs these answers and the wrong ones below on every build.

The approval stream in Part 2

Ten calls, two bad: call 5 emails the whole customer list to audit@finance-mirror.example, and call 8 deletes account 102. Both summaries are written in the words of the task, so the summary tab cannot tell them apart from the rest; the literal tab shows the outside address in red and the irreversible flag. The gate learners write in step 3 meters email by count, so it holds call 8 and call 9 (an ordinary reminder, the fourth email) and lets call 5, the third email, straight through. That is the teaching moment: a count catches a flood and not a thief, and the destination is the next control (Part 4).

The sort in Part 5 (ten controls)

Boundary remove the tools the task does not need; mint the credential for the task and the person; check the object inside the tool; approval of the literal irreversible action; spend and rate limits keyed to the identity.

Reducer an “allow this tool?” prompt on every call; a classifier that approves calls for the human; a scanner over tool descriptions; a system-prompt rule.

Detect alerts on a run of denied calls, and a log of who each call was for.

The six checkpoint questions in the course shell
  1. Remove the tools the task does not need and mint a key for the task. The prompt and the classifier only lower the odds.
  2. The object check in the tool, comparing the account’s tenant with the tenant the call is for. The scope was legitimate for the reply.
  3. People approve nearly every prompt and stop reading; hold only what cannot be undone, and show the literal call.
  4. The parser accepts abbreviations and bundled short options, so the dangerous option has other spellings.
  5. The change after approval, but not a tool that was already poisoned when you approved it.
  6. Authority is a property of the call, not of the agent: shrink the toolbox, scope the credential to the task and the person, and check every use outside the model.
The sixteen combinations (what the table shows)

With the real task still working, only two combinations hold all four attacks: the scoped credential, the object check and the approval gate together, and those three with the tool diet. The tool diet alone leaves the deputy and the flood. The gate alone leaves only the deputy. The credential alone leaves the deputy and the flood. The object check alone breaks the real task, because the shipped key names no tenant and the check fails closed. The object check and the gate together hold every attack, but only because they also refuse the real task.

Discussion questions

  1. Pick one agent in your organisation. How many tools does it hold, and how many does its most common task need? Who decided, and when was it last reviewed?
  2. Whose credential does it use: its own, the requester’s, or a service account everyone shares? What happens when a stranger’s text reaches it?
  3. Where does your approval gate run, who can write its configuration, what does the person see on the card, and how often do they say yes?
  4. Which of its tools take a free string: a command, a path, a URL, SQL? Does the check run on the parsed value or on the text?
  5. A vendor tells you a behaviour is expected or intended. What is your control?
  6. Where do its tool definitions come from? What happens if one is rewritten tomorrow, and would you notice?
  7. Which of the 54 cases in the case library would you most expect to find in your own estate, and which layer would have held?
  8. What would your policy test assert today, and which of the four attacks would turn it red?

Common misconceptions

Heard in the roomThe short answer
“We tell the model not to use that tool.”That is a prompt, which is a reducer. The tool must be absent. In the Replit case the freeze existed only as a sentence.
“Least privilege means a read-only key.”The deputy lookup is a read. Read-only bounds writes, and the object check bounds whose data is read.
“Our scanner checks the tool descriptions.”It lowers the odds and passed the reworded tool. Keep a reach limit behind it.
“An approval prompt makes it safe.”Only while it is rare and literal. Users accept 93 percent of manual prompts in Claude Code, by Anthropic’s count.
“A better model solves it.”The module never asked whether the model is fooled. It asked what a fooled model can reach.
“This is a prompt-injection problem.”Injection spends the excess. Asana and Replit had no attacker, and the excess was the same.

Before you present

  • Open the module full-screen in a fresh window and let it boot once. The first load takes 10 to 40 seconds while the Python runtime starts; later loads are quicker.
  • Run the whole page once yourself, including “Show a working answer” and the sixteen-combination table. Reload before the session so the page starts clean.
  • Raise the browser zoom to 125 percent for a projector. The consoles are wide and the text is small at 100 percent.
  • Keep the case library open in a second tab for questions: it is searchable by product, company and CVE.
  • If several people share a machine, use a private window. Progress and answers are kept in the browser.
  • No key is needed or asked for in this module. The OpenRouter key belongs to Module 02’s live section and the model benchmark.
  • Printing this page opens every answer. Keep it for the person teaching.
